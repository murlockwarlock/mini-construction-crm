# Решения

- Используется один облачный Supabase-проект, один GitHub-репозиторий и один сервер. Staging и отдельный deploy workflow не добавляются.
- Soft-delete скрывает объекты и задачи из рабочих списков. Постановщик может открыть удалённую запись и её историю для аудита; исполнитель удалённые записи не видит. Изменение статуса и повторное удаление удалённой задачи запрещены.
- История статусов хранится отдельно и создаётся в той же транзакции, что и смена статуса. Прямой DML истории запрещён.
- pgTAP включается только в CI перед тестом базы и не устанавливается production-миграцией.
- В выбранном Supabase-проекте сейчас нет прикладных таблиц и миграций. Auth REST фактически возвращает `disable_signup: true`. Через доступный MCP нет операции изменения Auth-настройки; при необходимости ручное действие: Supabase Dashboard → Authentication → Settings → User Signups → отключить регистрацию.
- Визуальные эталоны создаются реальными Playwright-снимками в CI-артефактах. Фиктивные PNG и автоматическое обновление baseline в репозитории не используются; снимки требуют человеческого утверждения.
- Приложение и облачная схема на этом этапе не деплоятся. Остаётся проверить применение миграции к выбранному облачному проекту после зелёного CI.
